## 一、痛点：vnpy 很强，但官方形态是"单机桌面"

[vnpy](https://github.com/vnpy/vnpy)（VeighNa）是国内最主流的开源量化框架，但它官方默认是 **PySide6 桌面客户端**：

- 跑在本机，图形界面操作；
- 单机、单人，难做到"团队共用、多用户隔离"；
- 服务器上不好跑（要图形环境 / 远程桌面）。

很多团队真正想要的是：**一台服务器跑引擎，大家用浏览器登录交易**——这就是 B/S 化。

## 二、本项目做了什么：vnpy 的"Web 壳"

一句话：把 vnpy 从"桌面终端"改造成"**B/S 架构的团队交易终端**"。

```
┌─────────────────────────────────────────────┐
│  Vue 3 前端（浏览器 SPA）                     │
│  登录 / 行情 / 分时K线 / 下单 / 委托 / 持仓 / 管理 │
└───────────────┬─────────────────────────────┘
                │ HTTPS / WSS（REST + WebSocket）
┌───────────────▼─────────────────────────────┐
│  API 服务层（FastAPI + Uvicorn）              │
│  REST：下单/撤单/配置/查询  WS：实时推送        │
│  认证(JWT) · 权限 · 风控 · 审计               │
└───────────────┬─────────────────────────────┘
                │ 进程内调用（同一个 Python 进程）
┌───────────────▼─────────────────────────────┐
│  vnpy 引擎核心（headless，不 import Qt）       │
│  MainEngine + EventEngine + 多 CTP Gateway    │
└───────────────┬─────────────────────────────┘
                │
┌───────────────▼─────────────────────────────┐
│  存储：MySQL（业务）+ ClickHouse（Tick，可选）  │
└─────────────────────────────────────────────┘
```

![Stabx 系统架构图](https://stabx-dev.oss-cn-beijing.aliyuncs.com/mystabx/docs/images/architecture.png)

**关键点**：vnpy 的 `MainEngine` / `EventEngine` **不依赖 Qt**，可以纯后台跑；前端所有动作通过 API 转成对 `MainEngine` 的方法调用，vnpy 的事件引擎把 tick/委托/持仓广播出来，由桥接层转发到 WebSocket。

## 三、技术选型与理由

| 层 | 选型 | 为什么 |
|---|---|---|
| 前端框架 | Vue 3 + Vite + TypeScript | 组合式 API、生态成熟 |
| UI 组件 | Element Plus | 表格/表单/弹窗齐全 |
| 图表 | ECharts | 分时图、K 线、资金曲线 |
| 状态 | Pinia + Vue Router | 轻量、类型友好 |
| 实时通信 | 原生 WebSocket | 心跳 + 断线重连 |
| 后端 | FastAPI + Uvicorn | 异步、自带 OpenAPI 文档 |
| 引擎 | vnpy `MainEngine`/`EventEngine` | headless，进程内单例 |
| 认证 | JWT + bcrypt | 登录态与权限 |
| 业务库 | MySQL（SQLAlchemy） | 多用户/账户/会话/订阅等 |
| 时序库 | ClickHouse（可选） | 只存 Tick，软失败 |

## 四、几条关键设计决策（先记住，后面会展开）

1. **产品入口是 Web，不是桌面 Qt**：`./start.sh` 一键起（构建 SPA + uvicorn 托管）。
2. **不要对 vnpy 引擎用 `uvicorn --workers`**：`MainEngine` 必须在同一进程，多 worker 会各自起一份引擎、互相打架。
3. **每用户独立 CTP 账户 + 用户级隔离**：一个管理员标志，不做复杂 RBAC。
4. **时序和业务分层**：高频 Tick 走 ClickHouse（可软失败），低频业务（用户/账户/会话/订阅）走 MySQL。

## 五、小结

- vnpy 负责"引擎与柜台"，本项目负责"Web UI + FastAPI 托管层"，**不重新实现撮合/协议**；
- 技术栈：Vue 3 + FastAPI + headless vnpy + MySQL(+ClickHouse)；
- 下一篇开始动手：先把 Python / Node / MySQL / CTP 环境装齐。
